# blood-pressure

Suivi de l'automesure tensionnelle (règle du 3-3-3), PWA auto-hébergée. Le vocabulaire du domaine est dans `GLOSSARY.md`, les décisions dans `docs/adr/`, et leur contexte historique dans `docs/HISTORIQUE.md`.

## Conventions

- **Next.js** : la version installée a des changements incompatibles avec ce que tu connais. Lire le guide concerné dans `node_modules/next/dist/docs/` avant d'écrire du code, et tenir compte des dépréciations. `next build` vérifie les types avec `tsconfig.build.json`, sans `e2e/` ni `playwright.config.ts`, qui sont hors du contexte Docker (`.dockerignore`).
- **Arborescence** : `src/app/` (pages Next.js et route `/rpc` ; pages connectées dans le groupe `(app)/`, espace admin dans `admin/`), `src/components/` (coquille, navigation ; `ui/` : composants shadcn/ui), `src/i18n/` (langues et catalogues), `src/server/router/` (une procédure oRPC par fichier, regroupées dans `index.ts`), `src/server/db/` (schéma Drizzle et connexion), `src/worker/` (service `worker`), `src/lib/` (code client), `drizzle/` (migrations SQL commitées), `e2e/` (Playwright). Le domaine pur est dans `src/domain/`, sans import de base ni de framework : validation des mesures et valeur d'alerte (`measurement.ts`), moments et jours des créneaux (`slot.ts`), jours du calendrier dans un fuseau (`local-date.ts`), campagnes (`campaign.ts`, voir **Campagnes**), référentiels et série des statistiques (`guideline.ts`, `stats.ts`, voir **Statistiques et référentiels**), compte rendu (`report.ts`), rappels (`reminder.ts`). Il est partagé par les formulaires et par le routeur (schémas zod qui appellent le domaine : `router/measurement-input.ts`).
- **API** : toute donnée passe par le routeur oRPC (`src/server/router`), consommé côté client avec `orpc.<procédure>.queryOptions()` (TanStack Query), servi en HTTP par `handleRpc` (`router/rpc-handler.ts`, corps limité à `RPC_MAX_BODY_BYTES`). Les procédures partent de `base` (`router/base.ts`) et reçoivent leurs dépendances par le contexte (`AppContext`), jamais par un import global : c'est ce qui les rend testables. L'instant présent aussi : `currentTime(context)` (jamais `new Date()` pour une règle métier), fixé dans les tests par `api.as(headers, { now })`.
- **Authentification** : better-auth (`src/server/auth/`), routes `/api/auth/...`. Une procédure protégée part de `authed` (appelant connecté, `context.user`) ou de `adminOnly` (`router/authed.ts`), jamais de `base`. L'admin vient du `.env` et est créé ou mis à jour au démarrage (`src/instrumentation.ts`, `ensureAdmin`) : un nouveau mot de passe révoque ses sessions, un nouvel email supprime l'ancien compte admin. Il ne change pas son mot de passe dans l'app (`account.changePassword` part de `userOnly`). Le plugin admin de better-auth n'a que les droits utilisés par les procédures `admin.*` (pas d'usurpation d'identité), et ses routes HTTP `/api/auth/admin/*` sont toutes fermées (`disabledPaths`, vérifié par `auth/admin-routes.int.test.ts`). Pages serveur : `requireUser()`.
- **Admin et données de santé** (ADR-0004) : toute procédure qui lit ou écrit des données d'un utilisateur (mesures, campagnes, compte rendu, export, rappels…) part de `userOnly` (`router/authed.ts`), qui renvoie `FORBIDDEN` à l'admin. `router/access.int.test.ts` parcourt tout le routeur : chaque procédure hors `admin.*` et hors de sa liste `ADMIN_ALLOWED` doit refuser l'admin, et chaque `admin.*` doit refuser un utilisateur ordinaire. Une nouvelle procédure est donc testée d'office ; ne l'ajouter à `ADMIN_ALLOWED` que si elle ne touche aucune donnée d'un utilisateur. Les procédures de l'admin sur un compte : `adminOnly.input(managedUserInput).use(requireManagedUser)` (`router/managed-user.ts`, `NOT_FOUND` pour un id inconnu ou l'admin lui-même).
- **Gestion des comptes** : désactivation, suppression, réinitialisation et révocation passent par le plugin admin de better-auth (`context.auth.api.*`). Une table qui appartient à un utilisateur référence `user.id` avec `onDelete: "cascade"` : c'est ce qui fait que la suppression d'un compte efface toutes ses données (vérifié pour toutes les tables par `src/server/db/user-data.int.test.ts`). L'inscription libre est un réglage de l'instance (table `app_settings`, une seule ligne, `src/server/settings/app-settings.ts`) que l'admin ouvre ou ferme ; un hook better-auth refuse `/sign-up/email` quand elle est fermée (par défaut). Pas de variable d'environnement pour ce réglage. L'utilisateur supprime lui-même son compte par `account.delete` (mot de passe vérifié, sessions supprimées ; la route `/api/auth/delete-user` de better-auth reste désactivée) et exporte ses mesures par `account.exportMeasurements` (CSV construit par `src/server/export/measurements-csv.ts`, heure dans le fuseau des réglages, campagnes manquées et sautées en lignes sans valeurs) : carte « Mes données » des réglages, absente pour l'admin.
- **Textes de l'interface** : aucun texte en dur. Chaque texte a une clé dans `src/i18n/messages/fr.json` **et** `en.json` (mêmes clés, vérifié par `src/i18n/messages.test.ts` ; le français fait foi pour le typage des clés). Les termes suivent `GLOSSARY.md` : le terme français en FR, son nom anglais en EN (Mesure / Measurement, Compte rendu / Report…). Composant serveur : `await getTranslations("section")` ; composant client : `useTranslations("section")`. Un message d'erreur du serveur n'est pas affiché tel quel : le client traduit selon le `code` de l'`ORPCError`. Pas de langue dans l'URL : `src/i18n/request.ts` prend la langue des réglages de l'utilisateur, sinon celle du navigateur, sinon le français (`resolveLocale`).
- **Interface** : Tailwind v4 et shadcn/ui (`pnpm dlx shadcn@3 add <composant>`, puis vérifier que `cn` vient de `@/lib/utils`), icônes lucide, pensée mobile d'abord (utilisable à 360 px). Thème : `<html data-theme="light|dark|system">` rendu par le serveur depuis les réglages, couleurs choisies en CSS seul (`src/app/globals.css`, variante `dark:`) : pas de script, donc pas de flash. Une page connectée va sous `src/app/(app)/` (coquille `AppShell` : en-tête, déconnexion, barre de navigation en bas). Pour l'ajouter à la navigation : une entrée dans `src/components/nav-items.ts` (`userNav` ou `adminNav`) et son libellé `nav.<clé>` dans les deux catalogues. Les pages de l'admin vont sous `src/app/admin/` (layout réservé à l'admin, `requireAdmin()` aussi dans chaque page).
- **Réglages de l'utilisateur** : table `user_settings` (une ligne par utilisateur, créée au premier enregistrement ; sans ligne, valeurs par défaut), lue et écrite par `settings.get` et `settings.update`. Le nom affiché reste `user.name` (better-auth). Un nouveau réglage : une colonne avec une valeur par défaut, et un champ facultatif dans `settings.update`. Le fuseau (`time_zone`, IANA) vaut `null` tant que celui du navigateur n'a pas été enregistré (`TimeZoneDetector`, rendu par le layout `(app)`), et `DEFAULT_TIME_ZONE` s'applique en attendant ; next-intl affiche les dates dans ce fuseau (`src/i18n/request.ts`). Ces réglages (y compris fuseau et fréquence) ne sont pas des données de santé : `settings.*` reste dans `ADMIN_ALLOWED`.
- **Campagnes** (`GLOSSARY.md`, ADR-0005, ADR-0006, ADR-0011) : module pur `src/domain/campaign.ts`. En base (table `campaign`, jours locaux) : la date prévue, le statut d'une campagne sans mesure s'il est enregistré (`missed` ou `skipped`, sinon `null`), `original_start` pour un rattrapage, `skipped_on`. Chaque mesure de campagne porte son créneau (`campaign_id`, `campaign_day`, `moment`). Le reste est calculé à partir de `CampaignInput` (campagnes, mesures, fréquence, fuseau, instant présent).
  - `campaignOverview(input)` : chaque campagne (`CampaignView` : statut `planned`/`inProgress`/`finished` (complète)/`incomplete`/`missed`/`skipped`, début prévu et réel, rattrapage, 6 créneaux, complétude sur 18, créneaux manquants, moyennes), y compris les manquées seulement calculées (`id: null`). Aussi la campagne en cours, les créneaux du jour et la prochaine campagne (`next` : enregistrée, ou calculée avec `campaignId: null` ; `late`, `catchUp`, `skippable`, `startBy`). C'est l'entrée des statistiques, du compte rendu, de l'export et des rappels. « Terminée » du glossaire : `isFinished(view)` ; 18/18 : `isComplete(view)`.
  - Début en retard : une première mesure commence une campagne de J+0 à J+6 (`LATE_START_DAYS`). Sans mesure, elle est manquée et un rattrapage est prévu le lendemain de sa fenêtre, en boucle tant qu'il est manqué. Sautée : la suivante part de la date prévue initiale plus la fréquence (ou du jour du saut plus la fréquence si elle est passée). Pour une campagne reportée, c'est la date reportée ; pour un rattrapage reporté, la date de la campagne manquée d'origine.
  - `attachMeasurement(input, takenAt)` : le créneau d'une saisie selon son horodatage (saisie a posteriori). Elle peut aller dans une campagne commencée, ou commencer une campagne planifiée ou manquée postérieure à la dernière commencée (`dropCatchUps` : les rattrapages à supprimer), sinon c'est une mesure libre. Une campagne sautée ne reçoit rien. L'ordre de saisie ne compte pas : une mesure antérieure au début réel, mais dans la fenêtre de début, avance ce début si les 3 jours couvrent encore toutes les mesures (`renumber` : leur nouveau jour) ; sinon elle est libre.
  - `scheduleCampaign(input, start)` : planifier la première campagne, ou avancer ou reporter la prochaine (un rattrapage le reste). `skipCampaign(input)` : sauter la prochaine si elle est en retard ou de rattrapage.
  - `missedCampaignsToRecord(input)` : les manquées dont le statut n'est pas encore enregistré. Le worker les enregistre (`src/worker/missed-campaigns.ts`, file `missed-campaigns` chaque quart d'heure), et le routeur aussi avant toute création de campagne (`insertCampaign`, `src/server/campaigns/missed.ts`). La vue est la même avant et après : ne jamais faire dépendre l'affichage du worker.
  - Côté serveur : `loadCampaignInput(db, userId, now)` (`src/server/campaigns/`) lit l'entrée du domaine, `slotColumns` rattache une saisie (`measurements.create` et `.update`). Procédures `campaigns.overview`, `campaigns.schedule`, `campaigns.skip` et `campaigns.delete` (supprime ses mesures par la clé étrangère en cascade ; `CONFLICT` pour une campagne manquée ou sautée, qui fait partie de l'historique : `isDeletable`). Tout jour se compte avec `localDateOf(instant, timeZone)` (`local-date.ts`), jamais en millisecondes, pour rester juste au changement d'heure ; le moment matin/soir avec `momentAt(instant, timeZone)` (`slot.ts`), dans le fuseau des réglages.
- **Statistiques et référentiels** (`GLOSSARY.md` : Référentiel, Seuil ; ADR-0007, ADR-0008) : la table des référentiels est une constante de `src/domain/guideline.ts` (`GUIDELINES` : sigle, nom complet et explication en FR et EN, seuil d'automesure ; SFHTA par défaut). Le choix est le réglage `guideline` (`user_settings`, `settings.update`), sans pays. `positionOf(moyenne, seuil)` renvoie `below` ou `above` (dès que la systolique **ou** la diastolique atteint le seuil). `src/domain/stats.ts` lit `campaignOverview` sans rien recalculer : `campaignSeries` (un point par campagne terminée, complète ou non ; ni campagne en cours, ni mesure libre) et `latestStanding` (dernière campagne terminée et sa position). Graphique réutilisable (statistiques, compte rendu) : `<CampaignChart points threshold thresholdLabel />` (`src/components/campaign-chart.tsx`, Recharts, composant client), point creux et n/18 en info-bulle pour une campagne incomplète, seuil en deux lignes pointillées, couleurs `--chart-systolic` et `--chart-diastolic` de `globals.css` (clair et sombre), tableau masqué pour les lecteurs d'écran. Toute interprétation affiche « Ne remplace pas un avis médical » (`stats.disclaimer`) et n'emploie jamais « hypertension » comme diagnostic. Les mesures libres sont listées à part (`campaignId === null`).
- **Compte rendu** (`GLOSSARY.md` : Compte rendu, Campagne incomplète) : `src/domain/report.ts`, `reportOf(overview, période)` lit `campaignOverview` sans rien recalculer par campagne. Procédure `report.get({ period })`.
  - Périodes `REPORT_PERIODS` (`lastCampaign`, `oneYear`, `fiveYears`, `all`) : campagnes terminées (complètes ou non) dont le début réel est au plus 12 ou 60 mois avant aujourd'hui, borne comprise. Chaque campagne porte son écart de moyenne globale avec la campagne terminée précédente, même hors période.
  - Résumé : moyennes globale, matin et soir de toutes les mesures de la période (moyennes de campagne pondérées par leur nombre de mesures), nombre de campagnes, part de complètes, nombre de manquées et de sautées (`missedCount`, `skippedCount`, affichés même sans campagne terminée). Les manquées et sautées de la période sont listées à part (`Report.absent`, section « Campagnes manquées ou sautées »).
  - Page `src/app/(app)/report/` : le CSS d'impression passe par les variantes `print:` de Tailwind (commandes masquées, tableau des mesures rendu une seconde fois en `hidden print:block` car un `<details>` fermé ne s'imprime pas) ; le bouton « Imprimer / PDF » appelle `window.print()`.
- **PWA et hors ligne** (ADR-0002, ADR-0010) :
  - Manifeste `src/app/manifest.ts` (contenu dans `src/lib/web-manifest.ts`), icônes `public/icons/` (PNG commités, régénérés depuis les SVG par `pnpm icons`, avec ImageMagick ; `pnpm build` copie `public/` dans le standalone). Instructions d'installation : page `/install`, liée depuis les réglages.
  - Service worker Serwist : source `src/app/sw.ts`, compilé et servi à `/serwist/sw.js` par `src/app/serwist/[path]/route.ts`, enregistré en production seulement (`src/app/providers.tsx`). Il précache les ressources statiques et la page publique `/offline`, ne met **aucune** page connectée ni `/rpc` en cache, et sert `/offline` à une navigation sans réseau. Gestionnaires `push` (affiche le `PushMessage`) et `notificationclick` (ouvre sa page dans une fenêtre de l'app) dans `src/app/sw.ts`.
  - Sans réseau, `OfflineBanner` s'affiche dans `AppShell`. Tout formulaire qui enregistre : `const online = useOnline()` (`src/lib/use-online.ts`) et `disabled={!online || pending}` sur son bouton. Pas de file d'attente hors ligne.
  - Formulaire de saisie d'un créneau : passage seul au champ suivant (`isEntryValueComplete`, `measurement.ts` : quand aucun chiffre de plus ne resterait dans les bornes) et minuteur du protocole (`src/domain/protocol-timer.ts` : 5 min de repos, puis 1 min relancée par le premier chiffre des mesures 1 et 2, même en pause ; pause, reprise et recommencer ; composant `entry/measurement-timer.tsx`, signal `src/lib/alarm.ts`). Chacun peut passer en manuel depuis la page de saisie (réglages `entryAutoAdvance`, `entryAutoTimer`, `entry/entry-modes.tsx`).
  - Un formulaire de saisie garde son brouillon avec `useDraft(user.id, "<formulaire>", valeursInitiales)` (`src/lib/use-draft.ts`) : champs contrôlés par `value` et `setValue`, `clear(prochainesValeurs?)` après un enregistrement réussi (exemple : `src/app/(app)/entry/measurement-form.tsx`) ; le brouillon (`localStorage`, par utilisateur et par formulaire) est relu après l'hydratation (`restored` passe à `true`).
- **Premier lancement et rappels** (ADR-0002, ADR-0003) : page `/welcome` (`src/app/(app)/welcome/`), quatre étapes passables (protocole `src/components/protocol.tsx`, installation, notifications, rappels), ouverte d'office une seule fois par l'accueil tant que `user_settings.onboarded` est faux (marqué dès la première étape franchie), puis depuis les Réglages. L'admin ne la voit pas. Préférences de rappel (heures du matin et du soir `HH:MM`, rappel la veille, relance et son délai) : domaine `src/domain/reminder.ts`, colonnes de `user_settings`, lues et écrites par `settings.get`/`settings.update` (pas des données de santé).
- **Notifications push** : module serveur partagé `src/server/push/` (app et worker).
  - Clés VAPID générées au premier démarrage et stockées en base (table `vapid_keys`, une ligne) par `ensureVapidKeys(db)` (`vapid.ts`, appelé par `src/instrumentation.ts`) : jamais dans le `.env` ni le dépôt. Abonnements : table `push_subscription` (un appareil par `endpoint`, unique).
  - Envoi : interface `PushSender` (`sender.ts`, `send(cible, message)` → `"sent"` ou `"gone"`), implémentée par `createWebPushSender({ db, subject })` (subject = `APP_URL`) ; `getPushSender()` (`push/index.ts`) donne celle du processus. La requête est préparée par `web-push` (`generateRequestDetails`) mais envoyée par `createWebPushTransport` (`transport.ts`) : coupée au bout de `PUSH_SEND_TIMEOUT_MS` au total (pas seulement d'inactivité), réponse lue sur `PUSH_MAX_RESPONSE_BYTES` au plus, aucune exception hors de la promesse. Seuls les tests remplacent sa connexion (`connection`, service push local en HTTP).
  - Protection SSRF (`push/endpoint.ts`) : `push.subscribe` n'accepte qu'une adresse HTTPS publique (`isAllowedPushEndpoint` : ni IP privée, locale ou réservée, ni nom local), l'envoi revérifie (un abonnement refusé est traité comme expiré) et se connecte par `pushAgent`, qui refuse un nom résolu vers une adresse non publique.
  - `sendToUser(db, sender, userId, message)` envoie à tous les appareils d'un utilisateur et supprime les abonnements expirés : c'est l'entrée à réutiliser par le worker. Les procédures reçoivent l'envoi par `context.push` (faux en test : `createTestApi({ push })`). Message : `PushMessage` (`src/lib/push-message.ts`, `{ title, body, url, tag? }`), lu par le service worker (`parsePushMessage`, qui n'ouvre qu'un chemin de l'app). Textes traduits hors requête : `translator(locale)` (`src/i18n/translator.ts`).
  - Procédures `push.publicKey`, `push.subscribe`, `push.unsubscribe`, `push.sendTest` (limitée par utilisateur : `SEND_TEST_LIMIT`, middleware `limitPerUser` de `router/rate-limit.ts`, comme `limitPasswordAttempts`), toutes `userOnly`. Côté navigateur : `src/lib/push-client.ts` et la carte `NotificationCard` (sur iOS hors PWA installée, elle explique qu'il faut d'abord installer l'app). En développement, le service worker n'est pas enregistré : les notifications y sont « non prises en charge ».
- **Rappels envoyés par le worker** (ADR-0003) : `src/worker/main.ts` démarre pg-boss sur la même base (schéma `pgboss`) et lance la file `reminders` chaque minute (`policy: "singleton"`, sans nouvel essai, `missed: "skip"`) ; SIGTERM attend la fin de la tâche en cours.
  - Tâche `runReminders({ db, sender, now })` (`src/worker/reminders.ts`, testée avec un faux `PushSender` et une horloge fixée) : pour chaque utilisateur ayant un appareil abonné, préférences lues par `reminderPreferencesOf`, domaine `dueReminders` (`src/domain/reminder.ts`) sur `campaignOverview`, envoi par `sendToUser` (textes `reminders.*` via `translator`).
  - Journal `notification` (canal `push`, contrainte unique utilisateur + canal + `kind` + jour + moment). `claimReminder` écrit la ligne **avant** l'envoi : deux passages simultanés n'envoient qu'une fois. Si tous les appareils échouent, elle est retirée et le rappel réessayé la minute suivante.
  - Règles du domaine : rappel du créneau à l'heure du matin ou du soir (jour local, `instantAt`, juste au changement d'heure) pour les créneaux non remplis de `todaySlots`. Cela inclut chaque jour de la fenêtre de début d'une campagne en retard ou de rattrapage : les rappels suivent les rattrapages (ADR-0011). Relance après le délai : elle remplace le rappel si les deux sont en retard, et ne part pas après minuit. Rappel de la veille du début de `next`, à l'heure du soir.
  - Un rappel en retard (worker arrêté) part encore pendant `REMINDER_GRACE_MINUTES` (30), jamais après : pas de rafale au redémarrage (`docs/HISTORIQUE.md` §6.2).
- **Base** : modifier `src/server/db/schema.ts`, puis `pnpm db:generate` et committer la migration. Les migrations s'appliquent au démarrage du conteneur `app` (`docker/entrypoint.sh`).
- **Tests** (voir les points d'entrée validés) :
  - domaine pur : `*.test.ts` à côté du code, `pnpm test` ;
  - routeur oRPC contre un vrai Postgres : `*.int.test.ts`, `pnpm test:int`, via `createTestApi()` (`src/server/testing/test-api.ts`), qui crée une base jetable migrée par suite et appelle le routeur côté serveur (`api.client` anonyme, `api.as(headers)` connecté, `api.newUser(nom)` pour un utilisateur neuf à email unique, `api.admin()` pour la session de l'admin). `pnpm test:int` mélange l'ordre des tests (`--sequence.shuffle`) : chaque test crée ses propres utilisateurs et données, et une assertion sur une liste ne porte que sur ce que le test a créé. Il faut un Postgres joignable par `TEST_DATABASE_URL` (défaut `postgres://postgres:postgres@localhost:5432/postgres`), par exemple `docker run --rm -d -p 5432:5432 -e POSTGRES_PASSWORD=postgres postgres:17-alpine` ;
  - Playwright : `e2e/*.spec.ts`, `pnpm test:e2e` avec `DATABASE_URL` défini, uniquement pour les parcours clés. Importer `test` depuis `e2e/helpers.ts` (pas de `@playwright/test`) : chaque test y a sa propre IP cliente, sinon la limite de 5 connexions par minute et par IP fait échouer les tests en parallèle. Des campagnes passées (impossibles à planifier par l'interface) s'écrivent directement en base avec `e2e/seed.ts`.
- **Vérifications** avant de committer : `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:int` (et `pnpm test:backup` si `docker/backup.sh` change). La CI (`.github/workflows/ci.yml`) lance aussi Playwright, le build de l'image et gitleaks.
- **Déploiement** : une seule image (`Dockerfile`), commande `app` (migrations puis serveur Next.js standalone) ou `worker`. `docker-compose.yml` lance `app`, `worker`, `db` et `backup` (image Postgres, dump quotidien par `docker/backup.sh`, testé sans Docker par `pnpm test:backup` ; sans le schéma `pgboss`, dont les partitions font échouer `pg_restore --clean`). Le healthcheck de `app` appelle `/rpc/health`, qui interroge la base : la page `/health` répond 200 même base coupée. Toute nouvelle variable d'environnement est documentée dans `.env.template`. Un tag `vX.Y.Z` lance `.github/workflows/release.yml` : image amd64 et arm64 sur `ghcr.io/letoux/blood-pressure` (tags `vX.Y.Z`, `X.Y`, `latest`), puis une GitHub Release avec le compose épinglé sur cette image (généré par `src/scripts/release-compose.ts`, qui échoue si le compose ne contient plus `image: ${IMAGE:-…:latest}`, `build: .` et la config `file: ./docker/backup.sh`, ce script étant embarqué en ligne) et le `.env.template` (joint sous le nom `env.template`). **Repo public** : jamais de secret ni de `.env` commité.
