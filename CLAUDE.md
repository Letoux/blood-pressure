# blood-pressure

Suivi de l'automesure tensionnelle (règle du 3-3-3), PWA auto-hébergée. Le vocabulaire du domaine est dans `GLOSSARY.md`, les décisions dans `docs/adr/`, et leur contexte historique dans `docs/HISTORIQUE.md`.

## Conventions

- **Arborescence** : `src/app/` (pages Next.js et route `/rpc` ; pages connectées dans le groupe `(app)/`, espace admin dans `admin/`), `src/components/` (coquille, navigation ; `ui/` : composants shadcn/ui), `src/i18n/` (langues et catalogues), `src/server/router/` (une procédure oRPC par fichier, regroupées dans `index.ts`), `src/server/db/` (schéma Drizzle et connexion), `src/worker/` (service `worker`), `src/lib/` (code client), `drizzle/` (migrations SQL commitées), `e2e/` (Playwright). Le domaine pur est dans `src/domain/`, sans import de base ni de framework : validation des mesures et valeur d'alerte (`measurement.ts`), moments et jours des créneaux (`slot.ts`), jours du calendrier dans un fuseau (`local-date.ts`), campagnes (`campaign.ts`, voir **Campagnes**), référentiels et série des statistiques (`guideline.ts`, `stats.ts`, voir **Statistiques et référentiels**). Il est partagé par les formulaires et par le routeur (schémas zod qui appellent le domaine : `router/measurement-input.ts`).
- **API** : toute donnée passe par le routeur oRPC (`src/server/router`), consommé côté client avec `orpc.<procédure>.queryOptions()` (TanStack Query). Les procédures partent de `base` (`router/base.ts`) et reçoivent leurs dépendances par le contexte (`AppContext`), jamais par un import global : c'est ce qui les rend testables. L'instant présent aussi : `currentTime(context)` (jamais `new Date()` pour une règle métier), fixé dans les tests par `api.as(headers, { now })`.
- **Authentification** : better-auth (`src/server/auth/`), routes `/api/auth/...`. Une procédure protégée part de `authed` (appelant connecté, `context.user`) ou de `adminOnly` (`router/authed.ts`), jamais de `base`. L'admin vient du `.env` et est créé ou mis à jour au démarrage (`src/instrumentation.ts`). Pages serveur : `requireUser()`.
- **Admin et données de santé** (ADR-0004) : toute procédure qui lit ou écrit des données d'un utilisateur (mesures, campagnes, compte rendu, export, rappels…) part de `userOnly` (`router/authed.ts`), qui renvoie `FORBIDDEN` à l'admin. `router/access.int.test.ts` parcourt tout le routeur : chaque procédure hors `admin.*` et hors de sa liste `ADMIN_ALLOWED` doit refuser l'admin, et chaque `admin.*` doit refuser un utilisateur ordinaire. Une nouvelle procédure est donc testée d'office ; ne l'ajouter à `ADMIN_ALLOWED` que si elle ne touche aucune donnée d'un utilisateur. Les procédures de l'admin sur un compte : `adminOnly.input(managedUserInput).use(requireManagedUser)` (`router/managed-user.ts`, `NOT_FOUND` pour un id inconnu ou l'admin lui-même).
- **Gestion des comptes** : désactivation, suppression, réinitialisation et révocation passent par le plugin admin de better-auth (`context.auth.api.*`). Une table qui appartient à un utilisateur référence `user.id` avec `onDelete: "cascade"` : c'est ce qui fait que la suppression d'un compte efface toutes ses données (vérifié pour toutes les tables par `src/server/db/user-data.int.test.ts`). L'inscription libre est un réglage de l'instance (table `app_settings`, une seule ligne, `src/server/settings/app-settings.ts`) que l'admin ouvre ou ferme ; un hook better-auth refuse `/sign-up/email` quand elle est fermée (par défaut). Pas de variable d'environnement pour ce réglage. L'utilisateur supprime lui-même son compte par `account.delete` (mot de passe vérifié, sessions supprimées ; la route `/api/auth/delete-user` de better-auth reste désactivée) et exporte ses mesures par `account.exportMeasurements` (CSV construit par `src/server/export/measurements-csv.ts`, heure dans le fuseau envoyé par le navigateur) : carte « Mes données » des réglages, absente pour l'admin.
- **Textes de l'interface** : aucun texte en dur. Chaque texte a une clé dans `src/i18n/messages/fr.json` **et** `en.json` (mêmes clés, vérifié par `src/i18n/messages.test.ts` ; le français fait foi pour le typage des clés). Les termes suivent `GLOSSARY.md` : le terme français en FR, son nom anglais en EN (Mesure / Measurement, Compte rendu / Report…). Composant serveur : `await getTranslations("section")` ; composant client : `useTranslations("section")`. Un message d'erreur du serveur n'est pas affiché tel quel : le client traduit selon le `code` de l'`ORPCError`. Pas de langue dans l'URL : `src/i18n/request.ts` prend la langue des réglages de l'utilisateur, sinon celle du navigateur, sinon le français (`resolveLocale`).
- **Interface** : Tailwind v4 et shadcn/ui (`pnpm dlx shadcn@3 add <composant>`, puis vérifier que `cn` vient de `@/lib/utils`), icônes lucide, pensée mobile d'abord (utilisable à 360 px). Thème : `<html data-theme="light|dark|system">` rendu par le serveur depuis les réglages, couleurs choisies en CSS seul (`src/app/globals.css`, variante `dark:`) : pas de script, donc pas de flash. Une page connectée va sous `src/app/(app)/` (coquille `AppShell` : en-tête, déconnexion, barre de navigation en bas). Pour l'ajouter à la navigation : une entrée dans `src/components/nav-items.ts` (`userNav` ou `adminNav`) et son libellé `nav.<clé>` dans les deux catalogues ; une page pas encore construite rend `<ComingSoon />`. Les pages de l'admin vont sous `src/app/admin/` (layout réservé à l'admin, `requireAdmin()` aussi dans chaque page).
- **Réglages de l'utilisateur** : table `user_settings` (une ligne par utilisateur, créée au premier enregistrement ; sans ligne, valeurs par défaut), lue et écrite par `settings.get` et `settings.update`. Le nom affiché reste `user.name` (better-auth). Un nouveau réglage : une colonne avec une valeur par défaut, et un champ facultatif dans `settings.update`. Le fuseau (`time_zone`, IANA) vaut `null` tant que celui du navigateur n'a pas été enregistré (`TimeZoneDetector`, rendu par le layout `(app)`), et `DEFAULT_TIME_ZONE` s'applique en attendant ; next-intl affiche les dates dans ce fuseau (`src/i18n/request.ts`). Ces réglages (y compris fuseau et fréquence) ne sont pas des données de santé : `settings.*` reste dans `ADMIN_ALLOWED`.
- **Campagnes** (`GLOSSARY.md`, ADR-0005, ADR-0006) : module pur `src/domain/campaign.ts`. En base, seule la date de début prévue d'une campagne est stockée (table `campaign`, jour local) et chaque mesure de campagne porte son créneau (`campaign_id`, `campaign_day`, `moment`). Tout le reste est calculé, jamais stocké, à partir de `CampaignInput` (campagnes, mesures, fréquence, fuseau, instant présent) :
  - `campaignOverview(input)` : chaque campagne (`CampaignView` : statut `planned`/`inProgress`/`finished`/`incomplete`/`missed`, début prévu et réel, 6 créneaux, complétude sur 18 et créneaux manquants, moyennes globale/matin/soir sur toutes les mesures présentes), la campagne en cours, les créneaux du jour et la prochaine campagne (`next` : enregistrée, ou calculée avec `campaignId: null`). C'est l'entrée des statistiques, du compte rendu et des rappels ;
  - `attachMeasurement(input, takenAt)` : le créneau d'une saisie (libre, campagne existante, ou prochaine campagne calculée à enregistrer d'abord) ;
  - `scheduleCampaign(input, start)` : planifier la première campagne, ou avancer ou reporter la prochaine.
  - « Manquée » est calculé : une campagne sans mesure dont la période prévue (3 jours) est passée. La suivante est alors replanifiée au lendemain de cette période plus la fréquence, et ainsi de suite tant que des campagnes calculées passent sans mesure : il n'y a rien à écrire en base pour la replanifier (le worker lit `next`). Une prochaine campagne n'est enregistrée que lorsqu'on l'avance ou la reporte, ou qu'une saisie la commence.
  - Côté serveur : `loadCampaignInput(db, userId, now)` (`src/server/campaigns/`) lit l'entrée du domaine, `slotColumns` rattache une saisie (`measurements.create` et `.update`). Procédures `campaigns.overview`, `campaigns.schedule`, `campaigns.delete` (supprime ses mesures par la clé étrangère en cascade). Tout jour se compte avec `localDateOf(instant, timeZone)` (`local-date.ts`), jamais en millisecondes, pour rester juste au changement d'heure.
- **Statistiques et référentiels** (`GLOSSARY.md` : Référentiel, Seuil ; ADR-0007, ADR-0008) : la table des référentiels est une constante de `src/domain/guideline.ts` (`GUIDELINES` : sigle, nom complet et explication en FR et EN, seuil d'automesure ; SFHTA par défaut). Le choix est le réglage `guideline` (`user_settings`, `settings.update`), sans pays. `positionOf(moyenne, seuil)` renvoie `below` ou `above` (dès que la systolique **ou** la diastolique atteint le seuil). `src/domain/stats.ts` lit `campaignOverview` sans rien recalculer : `campaignSeries` (un point par campagne terminée, complète ou non ; ni campagne en cours, ni mesure libre) et `latestStanding` (dernière campagne terminée et sa position). Graphique réutilisable (statistiques, compte rendu) : `<CampaignChart points threshold thresholdLabel />` (`src/components/campaign-chart.tsx`, Recharts, composant client), point creux et n/18 en info-bulle pour une campagne incomplète, seuil en deux lignes pointillées, couleurs `--chart-systolic` et `--chart-diastolic` de `globals.css` (clair et sombre), tableau masqué pour les lecteurs d'écran. Toute interprétation affiche « Ne remplace pas un avis médical » (`stats.disclaimer`) et n'emploie jamais « hypertension » comme diagnostic. Les mesures libres sont listées à part (`campaignId === null`).
- **PWA et hors ligne** (ADR-0002, ADR-0010) : manifeste `src/app/manifest.ts` (contenu dans `src/lib/web-manifest.ts`), icônes `public/icons/` (PNG commités, régénérés depuis les SVG par `pnpm icons`, avec ImageMagick ; `pnpm build` copie `public/` dans le standalone). Service worker Serwist : source `src/app/sw.ts`, compilé et servi à `/serwist/sw.js` par `src/app/serwist/[path]/route.ts`, enregistré en production seulement (`src/app/providers.tsx`). Il précache les ressources statiques et la page publique `/offline`, ne met **aucune** page connectée ni `/rpc` en cache, et sert `/offline` à une navigation sans réseau. Gestionnaires `push` (affiche le `PushMessage`) et `notificationclick` (ouvre sa page dans une fenêtre de l'app) dans `src/app/sw.ts`. Sans réseau, `OfflineBanner` s'affiche dans `AppShell`. Tout formulaire qui enregistre : `const online = useOnline()` (`src/lib/use-online.ts`) et `disabled={!online || pending}` sur son bouton. Un formulaire de saisie garde son brouillon avec `useDraft(user.id, "<formulaire>", valeursInitiales)` (`src/lib/use-draft.ts`) : champs contrôlés par `value` et `setValue`, `clear(prochainesValeurs?)` après un enregistrement réussi (exemple : `src/app/(app)/entry/measurement-form.tsx`) ; le brouillon (`localStorage`, par utilisateur et par formulaire) est relu après l'hydratation (`restored` passe à `true`). Pas de file d'attente hors ligne. Instructions d'installation : page `/install`, liée depuis les réglages.
- **Premier lancement et rappels** (ADR-0002, ADR-0003) : page `/welcome` (`src/app/(app)/welcome/`), quatre étapes passables (protocole `src/components/protocol.tsx`, installation, notifications, rappels), ouverte d'office une seule fois par l'accueil tant que `user_settings.onboarded` est faux (marqué dès la première étape franchie), puis depuis les Réglages. L'admin ne la voit pas. Préférences de rappel (heures du matin et du soir `HH:MM`, rappel la veille, relance et son délai) : domaine `src/domain/reminder.ts`, colonnes de `user_settings`, lues et écrites par `settings.get`/`settings.update` (pas des données de santé).
- **Notifications push** : module serveur partagé `src/server/push/` (app et worker). Clés VAPID générées au premier démarrage et stockées en base (table `vapid_keys`, une ligne) par `ensureVapidKeys(db)` (`vapid.ts`, appelé par `src/instrumentation.ts`) : jamais dans le `.env` ni le dépôt. Abonnements : table `push_subscription` (un appareil par `endpoint`, unique). Envoi : interface `PushSender` (`sender.ts`, `send(cible, message)` → `"sent"` ou `"gone"`), implémentée par `createWebPushSender({ db, subject })` (librairie `web-push`, subject = `APP_URL`) ; `getPushSender()` (`push/index.ts`) donne celle du processus. `sendToUser(db, sender, userId, message)` envoie à tous les appareils d'un utilisateur et supprime les abonnements expirés : c'est l'entrée à réutiliser par le worker. Les procédures reçoivent l'envoi par `context.push` (faux en test : `createTestApi({ push })`). Message : `PushMessage` (`src/lib/push-message.ts`, `{ title, body, url, tag? }`), lu par le service worker (`parsePushMessage`, qui n'ouvre qu'un chemin de l'app). Textes traduits hors requête : `translator(locale)` (`src/i18n/translator.ts`). Procédures `push.publicKey`, `push.subscribe`, `push.unsubscribe`, `push.sendTest`, toutes `userOnly`. Côté navigateur : `src/lib/push-client.ts` et la carte `NotificationCard` (sur iOS hors PWA installée, elle explique qu'il faut d'abord installer l'app). En développement, le service worker n'est pas enregistré : les notifications y sont « non prises en charge ».
- **Rappels envoyés par le worker** (ADR-0003) : `src/worker/main.ts` démarre pg-boss sur la même base (schéma `pgboss`, géré par pg-boss) et lance la file `reminders` chaque minute (`policy: "singleton"`, sans nouvel essai, `missed: "skip"`) ; SIGTERM attend la fin de la tâche en cours. La tâche `runReminders({ db, sender, now })` (`src/worker/reminders.ts`, testée avec un faux `PushSender` et une horloge fixée) lit les utilisateurs ayant un appareil abonné, appelle le domaine `dueReminders` (`src/domain/reminder.ts`) sur `campaignOverview`, envoie par `sendToUser` (textes `reminders.*` via `translator`) et journalise dans `notification` (canal `push`, contrainte unique utilisateur + canal + type + jour + moment). La ligne est écrite **avant** l'envoi : deux passages simultanés n'envoient qu'une fois ; si tous les appareils échouent, elle est retirée et le rappel réessayé la minute suivante. Règles du domaine : rappel du créneau à l'heure du matin ou du soir (jour local, `instantAt` de `local-date.ts`, juste au changement d'heure) pour les créneaux non remplis de `todaySlots` ; relance après le délai, qui remplace le rappel si les deux sont en retard, et ne part pas après minuit ; rappel de la veille du début de `next` à l'heure du soir. Un rappel en retard (worker arrêté) part encore pendant `REMINDER_GRACE_MINUTES` (30), jamais après : pas de rafale au redémarrage. « Manquée » restant calculé, rien n'est écrit pour une campagne manquée : les rappels suivent `next`.
- **Base** : modifier `src/server/db/schema.ts`, puis `pnpm db:generate` et committer la migration. Les migrations s'appliquent au démarrage du conteneur `app` (`docker/entrypoint.sh`).
- **Tests** (voir les points d'entrée validés) :
  - domaine pur : `*.test.ts` à côté du code, `pnpm test` ;
  - routeur oRPC contre un vrai Postgres : `*.int.test.ts`, `pnpm test:int`, via `createTestApi()` (`src/server/testing/test-api.ts`), qui crée une base jetable migrée par suite et appelle le routeur côté serveur (`api.client` anonyme, `api.as(await api.signIn(email, mdp))` connecté, `ensureAdmin(api.auth, …)` pour l'admin). Il faut un Postgres joignable par `TEST_DATABASE_URL` (défaut `postgres://postgres:postgres@localhost:5432/postgres`), par exemple `docker run --rm -d -p 5432:5432 -e POSTGRES_PASSWORD=postgres postgres:17-alpine` ;
  - Playwright : `e2e/*.spec.ts`, `pnpm test:e2e` avec `DATABASE_URL` défini, uniquement pour les parcours clés. Importer `test` depuis `e2e/helpers.ts` (pas de `@playwright/test`) : chaque test y a sa propre IP cliente, sinon la limite de 5 connexions par minute et par IP fait échouer les tests en parallèle. Des campagnes passées (impossibles à planifier par l'interface) s'écrivent directement en base avec `e2e/seed.ts`.
- **Vérifications** avant de committer : `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:int` (et `pnpm test:backup` si `docker/backup.sh` change). La CI (`.github/workflows/ci.yml`) lance aussi Playwright, le build de l'image et gitleaks.
- **Déploiement** : une seule image (`Dockerfile`), commande `app` (migrations puis serveur Next.js standalone) ou `worker`. `docker-compose.yml` lance `app`, `worker`, `db` et `backup` (image Postgres, dump quotidien par `docker/backup.sh`, testé sans Docker par `pnpm test:backup`). Toute nouvelle variable d'environnement est documentée dans `.env.template`. Un tag `vX.Y.Z` lance `.github/workflows/release.yml` : image amd64 et arm64 sur `ghcr.io/letoux/blood-pressure` (tags `vX.Y.Z`, `X.Y`, `latest`), puis une GitHub Release avec le compose épinglé sur cette image (généré par `src/scripts/release-compose.ts`, qui échoue si le compose ne contient plus `image: ${IMAGE:-…:latest}`, `build: .` et la config `file: ./docker/backup.sh`, ce script étant embarqué en ligne) et le `.env.template` (joint sous le nom `env.template`). **Repo public** : jamais de secret ni de `.env` commité.
